Customizer Core

From login to order: how Customizer Core works

A sales rep logs in, designs an item, places the order, and tracks it through the factory. If the factory rejects the item, the rep fixes it and resubmits. Click a stage to jump to it. The green bars show how much of each stage's BRD is proven in code.

System at a glance

The browser runs a Vue 3 + Inertia front end. The Laravel app handles pages, carts and orders, and talks to the factory's Prolook API. Saved designs are the one exception: they go from the browser straight to Prolook.

Traced from the code in C:/Users/merin/laravel-docker/core/src/customizer-core. Paths below are relative to that folder.

STEP 1Login and session

Users log in with email and password. Each login fetches a Prolook API token and the user's role from QX7; there is no SSO.

What happens

  1. GET /login shows the Auth/Login page.
  2. POST /login → AuthenticatedSessionController@store:
    • checks the credentials and rejects accounts that were never activated (email_verified_at is empty);
    • Prolook::generateSessionToken stores pl_access_token in the session;
    • QX7::getAllUserInformationByEmail sets the role;
    • updates last_login.
  3. The user lands on one of these pages:
    • the update-password page, if the password must change;
    • the profile page, if a sales rep's details are incomplete;
    • the page they came from;
    • otherwise the home page /.
  4. HandleInertiaRequests shares data with every page, including rejected_order_items_count, the red badge on the Orders menu. The count is cached for 5 minutes and is always 0 for customers.

STEP 2Building an item in the customizer

The user picks a sport and style, then designs the item in the builder. They can save it as a design or add it to a cart.

What happens

  1. Pick a style: GET /sports/{sports}/designs, then GET /sports/{sports}/customize/{uniform_id} (SportController@showCustomizer). Reversible uniforms use sports.customize_reversible.
  2. Builder: the builderReskinEnabled flag picks BuilderReskin or the older Builder. It has a canvas and side panels: custom, fabric, color, piping, pattern, logo, roster, art, add-ons, text, layer and, during rework, issues.
  3. Colors: ReskinColorPickerModal.vue splits the palette by each color's core_color flag:
    • Core Colors on top;
    • Additional Colors below;
    • just Colors when the brand has no core colors.
  4. Save a design: Save & Share posts /saved_design straight to the Prolook API with the user's token, skipping Laravel. GET /saved-designs/{id}/customize reopens a saved design.
  5. Edit a cart item: GET /carts/items/{cartItem} opens the builder on that item.

The admin toggle that sets core_color (Colors By Brand page) is not in this repo; only the picker side is.

STEP 3Cart and placing the order

Adding to the cart saves a cart_items row and starts jobs that make thumbnails and the factory PDF. Placing the order sends the cart to Prolook and closes it.

What happens

  1. Add to cart: SelectCart.vue posts POST /carts/items (CartItemController@store).
    • Finds or creates the cart: the default cart, a new cart or a Team DB cart.
    • Creates the cart_items row, plus cart_items_side_b for reversible items.
    • Queues the jobs in order: low-res thumbnails, then full thumbnails, then GeneratePDFJob, then CartItemAnalyticsJob.
    • Marks the item complete if it has a design, a roster and application sizes, otherwise incomplete.
  2. Cart page: GET /shopping-cart. The roster is edited via PATCH /carts/items/{cartItem}/rosters.
  3. Submit: POST /orders/submit (Action\OrderController@submitOrder):
    • checks permission and validates the payment method (card or terms) and the sales rep;
    • creates the order and charges the card with Nexio, if paying by card;
    • sends the order to Prolook api/order/new and stores pl_order_code;
    • marks the cart completed;
    • sets each item's order_status = new, order_code and order_item_id, then sets temporary ship dates.
    If any step fails, the payment is voided and the database changes are rolled back.

STEP 4Order tracking

After submission, the factory reports each item's progress to the app. The Orders page shows the current status as a badge.

What happens

  1. Orders page: GET /users/orders. With the orderTrackingEnabled flag on, it shows OrderTrackerNew.vue, which loads rows from GET /api/orders/in-production.
  2. Drawers: clicking a row opens ItemView. Clicking the status badge opens OrderView.
  3. Factory updates: PUT /api/carts/items/{order_item_id}/track-status (Api\CartItemController@trackOrderStatus). The route has no login; it checks a shared key. Updates are saved in order_status_details with row locking.
  4. An update for an earlier step is stored but does not move the item backwards.

STEP 5On Hold and rework

When the factory rejects an item, the sales rep fixes the design in the builder and resubmits it. The item then goes back into production.

What happens

  1. Factory puts the item On Hold. It sends on_hold with rejection_reason, rejection_type, images and a date. The app sets on_hold.is_active = true and emails the order's sales rep (OrderOnHoldNotification).
  2. Rep is alerted. The email links to the item with action=fix-issue, and the Orders menu badge goes up by one.
  3. Fix Issue. The button shows on the Orders page and in the drawers, never for end users. useFixIssue.ts opens the item, or the reorder editor for reorders.
    • Access: managing reps and the order's own sales rep.
    • Rework mode turns on only when all of these hold: the link has fix-issue, the user has access, the item is On Hold, and the user is not an end user.
  4. Rework mode in the builder.
    • RejectionBanner.vue shows the "update only what is in the rework notes" message. VITE_REJECTION_BANNER_MESSAGE can override the text.
    • Issues & Logs shows the rejection reason and factory images: the header's Notes dropdown in the reskin builder, or a side panel in the classic builder.
    • The rep adds notes and attachments and answers "additional changes?". A justification is required when the answer is yes.
  5. Resolve and Submit. Builder.vue validates the form. ResolveAndSubmitModal.vue then confirms, and requires an agreement checkbox when there are additional changes.
  6. Resubmit (POST /carts/items/{cartItem}/resubmit-rejected-item). In one transaction it:
    • saves the new design;
    • uploads attachments to S3;
    • writes a fixed / rework change log;
    • calls api/order_item/update_rejection;
    • moves the item back to Artwork or Factory Production.
    Thumbnails and the PDF are then rebuilt (RegeneratePDFJob).
  7. Done. The rep returns to the Orders page with "Item Resubmitted".

STEP 6Reorder

"Reorder Item" copies a past order item into a cart with a new roster. The design stays locked to the original.

What happens

  1. Reorder button (OrderTrackerNew.vue → buyItAgain). It is hidden for reversible items and manual orders. Azure GET customizer/order/{orderCode} returns factory_order_id, part_id and order_item_id.
  2. Roster: with the reskin/order-tracking flag on, CreateRosterModal.vue opens (roster, then application sizes), then SelectCart. Otherwise GET /customize/{cartItem}/reorder opens CartItem/ShowReorder.
  3. Save: POST /carts/items/reorder (@storeReorder) copies the item with is_reorder = true, the original factory ids and the new roster, and clears the status and order code. Bulk reorders use /api/carts/store-reorders.
  4. Locked design: the builder shows a "LOCKED" badge ("Jersey design is locked to be sure the design is the same as the original design").

Reorders of legacy orders (the "REORDERS of Legacy Orders" BRD: price items, legacy orders page, deletion flow) have no code in this repo yet.

Data model and statuses

A user has carts, and a cart has items. Submitting a cart creates one order. Item progress lives in cart_items.order_status_details.

Status values

FieldValues
carts.statusactive, completed (abandoned is used in queries)
cart_items.statusincomplete, approved, change_request, pending_approval, complete
cart_items.order_statusnew, order_confirmed, artwork_production, factory_production, on_hold, shipped, pending_return, pending_cancel, returned, cancelled
order_status_details keystemporary_ship_date, order_confirmed, artwork_production, factory_production, on_hold, shipped, delivered (each with is_active)
changes_logs.typefixed, ask_for_changes, quick_change (issue_type: rework, system_update)
orders.hybris_order_statuspending, success, failed
